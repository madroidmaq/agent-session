Repository analysis · UI architecture decision

brainless UI 能否用于 Agent Session 主窗口？

问题 分析 theswerd/brainless 的功能，判断它是否是 UI 库，以及当前 macOS 主窗口能否按照其中的 UI 组件实现。
结论 仓库定位 当前架构 接入方式 组件映射 实施路线 来源
Decision

可以采用，但应移植设计与交互，而不是直接引入整个 React 组件库。

brainless 是 React + Tailwind 体系下的 shadcn Registry：它分发可复制的组件源码，不是传统 npm 运行时依赖，也不是完整 Agent 应用。

当前主窗口的 HTML/CSS/JS 展示层，天然适合承接它的消息、Thinking、Tool Call、Diff、Todo 等视觉模式。
现有 Swift 数据层、SQLite 搜索、文件监听与 WebKit Bridge 应继续保留，不应为套用 UI 而迁移。
直接使用 TSX 组件会额外引入 React、Tailwind、Vite 和资源打包链，收益不足以覆盖当前迁移成本。

01 · Repository identity

它是 UI 源码注册表，不是完整 Agent 产品

仓库的价值集中在高保真的 Coding Agent 终端界面，而不在模型、工具执行或会话基础设施。

它提供什么

形态shadcn Registry，安装时将 React/TSX 源码写入使用方项目。
技术栈React 19、Next.js 16、TypeScript、Tailwind CSS 4、Radix UI、Lucide。
组件Claude、Codex、Grok 风格的 Message、Thinking、Tool、Diff、Permission、Prompt、Slash Menu 等。
许可证MIT，可使用、复制和修改；实质性复制时需保留版权及许可声明。

它不提供什么

×不解析 Claude/Codex JSONL，也不管理真实会话。
×不执行命令、工具、Diff 计算或权限策略。
×不提供 LLM 调用、Agent Loop、持久化和桌面应用壳。
×部分界面展示快捷键提示，但源码未必实现对应完整行为。

03 · Integration options

三种接入方式

比较维度保持一致：架构影响、实施成本、复用程度与适用时机。

01直接使用 React 组件

新增 React、Tailwind 与前端构建链，把 TSX 编译成 WKWebView 可加载的静态资源。

import { ClaudeToolCall }
  from "./brainless/claude"

<ClaudeToolCall
  name="Bash"
  summary="23 passed"
/>
保留原组件结构，后续组件化能力强。
需要 React、Tailwind、Vite、SwiftPM 静态资源打包和新测试链。
成本：高架构影响：大当前：不推荐

02移植为原生 H5 组件

参考 brainless 的 DOM、状态与视觉层级，在现有 HTML/CSS/JS 中重新实现。

<details class="tool-call">
  <summary>
    ● Bash  23 passed
  </summary>
  <pre>...</pre>
</details>
不改变 Swift Bridge、数据模型、构建方式和 standalone 模式。
需要手工将 TSX/Tailwind 翻译为当前语义 CSS 与渲染函数。
成本：中架构影响：小当前推荐

03整体迁移为 React

将整个 template.html 重构为 React + TypeScript + Vite 的本地静态前端。

Swift/AppKit
      ↓ bridge
React + TypeScript
      ↓ vite build
Resources/web/*
长期组件边界、类型检查、状态管理和测试能力更好。
需迁移 Router、Bridge、Conversation 聚合、Demo 和资源打包。
成本：很高长期性：强未来再评估

推荐：方案 02

当前应用的核心是“读取、搜索和浏览会话”，现有 Web 层足以承载 brainless 的交互语言。先用原生 H5 方式重做组件，可获得大部分视觉收益，同时避免一次不必要的前端架构迁移。

只有在产品加入实时 Prompt、Permission、持续运行状态、复杂编辑和大量组件测试后，再重新评估方案 03。

04 · Component mapping

brainless 组件如何映射到当前主窗口

使用筛选按钮查看最适合左栏、中栏、右栏或未来功能的组件。

claude-message
codex-messageMessage

claude-thinkingThinking
中栏 Thinking

默认紧凑收起，显示状态与耗时，展开后阅读完整内容。

claude-tool-call
codex-execTool execution
中栏工具摘要

保留“状态 + 工具 + 简短结果”，完整输入输出继续放到右栏。

claude-diff
codex-diffDiff
右栏 Edit / MultiEdit 详情

采用结构化 add、del、ctx 行，但 Diff 计算仍由当前数据层负责。

claude-todo-listProgress
Agent 计划与任务进度

将 done、active、todo 转换为可扫描的真实进度，而非单一 Spinner。

grok-project-pickerNavigation
左栏项目筛选

借鉴紧凑路径、最近项目和键盘选择；不照搬完整终端外观。

grok-settings
grok-shortcutsUtility panel
详情 / 帮助面板

适合会话元数据、运行配置和快捷键帮助的高密度两栏展示。

grok-turn-endStatus
每轮对话末尾

以低优先级状态显示完成时间、耗时或 Token 摘要。

claude-prompt
claude-slash-menuComposer
未来交互式会话

只有主窗口从 Viewer 发展为可输入、执行和恢复的客户端后才需要。

claude-permission
codex-permissionsApproval
未来执行确认

必须接入真实风险信息、作用域、取消和审计，而不能只复制视觉。

05 · Recommended roadmap

建议实施路线

先建立可复用的 H5 Primitive，再按“中栏 → 右栏 → 左栏”的价值顺序推进。

01

提取 Design Token

将颜色、状态、字体、边框和间距收敛为变量。不要直接复制 brainless 写死的 Claude/Codex/Grok 品牌色。

template.html · :root自有视觉身份
02

建立无框架 UI Primitive

新增语义化的 Message、Thinking、Tool Call、Diff、Todo、Turn End 样式和渲染函数，避免继续堆叠一次性字符串模板。

agent-messageagent-thinkingagent-tool-callagent-diff
03

优先重做中栏阅读体验

首先统一消息排版、Thinking 渐进披露、工具摘要和 Tool Group。保留当前“中栏轻量摘要、右栏完整详情”的结构。
